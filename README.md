# BhooMiPredict

BhooMiPredict is a land acquisition delay monitoring prototype. It combines land, acquisition, court, compensation, and rehabilitation records into one case view and highlights cases that may need early intervention.

The project is designed as an SIH-style prototype using deterministic synthetic data. It is not connected to live government systems.

## What The Project Shows

- Case-level delay prediction
- High, medium, and low priority classification
- District-level risk overview
- Case details with land, court, payment, and rehabilitation information
- Plain-language reasons behind a case priority
- Suggested next action for each case
- Source department datasets and the joined case dataset
- Data-quality exceptions and alerts
- CSV download from the Data explorer page

## Architecture

```text
Synthetic source data
        |
        v
SQLite source tables
        |
        v
Identifier-based case linking
        |
        v
Latest case snapshot + joined case view
        |
        +--> Stage-aware XGBoost model
        +--> Priority score and recommendations
        +--> FastAPI service
        +--> Streamlit dashboard
```

## Source Datasets

The seed script creates five source tables:

| Department area | Table | Purpose |
|---|---|---|
| Land records | `dilrmp_parcels` | Parcel, owner type, land classification, and area |
| Land acquisition | `la_cases` | Case number, district, project type, current step, and affected families |
| Court records | `rccms_cases` | Court case and stay-order status |
| Compensation | `pfms_compensation` | Sanctioned and paid amounts |
| Rehabilitation | `rr_records` | Resettlement progress and grievances |
| Batch history | `case_snapshots` | 30-day refresh snapshots for stage and time-in-stage |

The `ulcid_registry` table links related records under one BhooMiPredict case ID.

Each case is also simulated through the full lifecycle: Notification, Survey, Declaration, Award, Compensation, Possession, and R&R. The seed data stores whether the case is completed and, for completed cases, the signed difference between actual and benchmark duration.

## How Records Are Joined

The current prototype uses identifiers rather than geometry:

- `la_cases.case_no` joins to `rccms_cases.case_no_ref`
- `la_cases.case_no` joins to `pfms_compensation.case_no_ref`
- `la_cases.case_no` joins to `rr_records.case_no_ref`
- `la_cases.ulpin` joins to `dilrmp_parcels.ulpin`
- `ulcid_registry` stores the final links and match confidence

Three seeded records are marked as fuzzy matches with lower confidence so the dashboard can demonstrate manual review.

The `case_snapshots` table stores periodic 30-day observations while a case remains in a stage. The joined feature frame uses only the most recent snapshot for each case; older snapshots remain available to demonstrate batch ingestion history.

The prototype does not currently perform a GIS spatial join. A production version can add PostGIS geometry fields and use operations such as `ST_Intersects`, `ST_Buffer`, and `ST_Intersection` to connect project alignments to affected parcels.

## Prediction Model

The project uses two separate XGBoost models with the same feature set.

The stage-aware classifier uses:

- Project type
- Current acquisition step
- Days in the current step
- Affected families
- Land area
- Historical district delay
- Court stay status
- Compensation paid ratio
- Rehabilitation progress
- Grievance count

The output includes:

- Chance of delay
- Priority score
- Priority level
- Main contributing reasons
- Suggested next action

The separate `delay_days_model.pkl` regressor predicts signed `actual_delay_days` and is trained only on completed cases, because ongoing cases do not yet have ground-truth outcomes. Training prints a held-out mean absolute error (MAE) in days. A negative delay means the simulated case finished ahead of its benchmark.

The Case details page includes a What-if simulator. It changes legal status, time in the current step, compensation progress, and rehabilitation progress, then reruns both models to show the before/after chance of delay and expected delay days.

The current prototype uses transparent rule-based explanations alongside the model output. SHAP is listed as a production explainability dependency for future model-level explanations.

## Setup On Windows

Open PowerShell in the project folder and activate the included environment:

```powershell
.\env\Scripts\Activate.ps1
```

If PowerShell blocks activation, run the commands with the environment Python directly as shown below.

Install dependencies if needed:

```powershell
.\env\Scripts\python.exe -m pip install -r requirements.txt
```

Create or refresh the synthetic database:

```powershell
.\env\Scripts\python.exe seed_data.py
```

Train the model:

```powershell
.\env\Scripts\python.exe train_model.py
```

Start the API in one terminal:

```powershell
.\env\Scripts\python.exe -m uvicorn main:app --host 127.0.0.1 --port 8000
```

Start the dashboard in a second terminal:

```powershell
.\env\Scripts\python.exe -m streamlit run app.py --server.port 8501
```

## Open The Application

- Dashboard: http://localhost:8501
- API documentation: http://localhost:8000/docs
- API health check: http://localhost:8000/health

## Main API Endpoints

| Endpoint | Purpose |
|---|---|
| `GET /overview` | Overall counts and district summary |
| `GET /risk-queue` | Cases ordered by priority |
| `GET /cases/{ulcid}` | Full case details |
| `GET /cases/{ulcid}/prediction` | Prediction and suggested action |
| `POST /cases/{ulcid}/what-if` | Compare original and modified predictions using parameter overrides |
| `GET /datasets` | Available source and joined datasets |
| `GET /datasets/{dataset_name}` | Rows and columns for a selected dataset |
| `GET /data-quality` | Unresolved data issues |
| `GET /alerts` | Unread alerts |

The What-if request accepts a JSON body such as:

```json
{
        "legal_dispute_flag": false,
        "days_in_current_stage": 10,
        "compensation_paid_ratio": 1.0,
        "rehabilitation_progress": 1.0
}
```

The prediction response includes `predicted_delay_days` and `predicted_delay_months` in addition to the existing priority output.

Dataset names contain spaces, for example:

```text
/datasets/joined%20case%20view
/datasets/payment%20records
```

## Dashboard Sections

### At a glance

Shows total cases, priority counts, records needing review, and district comparison.

### Cases needing attention

Provides a filterable worklist by priority and district.

### Case details

Shows one case as a readable story: acquisition progress, land and court status, compensation, rehabilitation, reasons for the priority, and suggested action.

The What-if panel lets users change key conditions and compare the original prediction with the modified prediction.

### Data explorer

Lets users inspect each source department table and the final joined dataset. Every table can be downloaded as CSV.

### Issues & alerts

Shows records requiring review and newly raised alerts.

## Prototype Data

The seed script creates 60 cases across:

- Paschim Burdwan
- Gaya
- Anantapur
- Nagpur
- Indore

All records are synthetic and intended for demonstration only. They must be replaced with authorized, validated government data before any operational use.

## Production Roadmap

1. Replace synthetic records with authorized data exchanges or APIs.
2. Add PostgreSQL and PostGIS as the production data layer.
3. Add geometry fields and true parcel-project spatial joins.
4. Add authentication, role-based access, and audit logging.
5. Add SHAP waterfall explanations and model version tracking.
6. Add scheduled retraining using observed case outcomes.
7. Add role-scoped views for district, state, and national officers.
